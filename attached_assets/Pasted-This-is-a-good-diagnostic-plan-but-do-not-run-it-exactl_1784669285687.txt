This is a good diagnostic plan, but **do not run it exactly as written yet**. A few corrections will make it safer and more reliable.

## What Replit got right

The pool-stats endpoint is appropriately narrow:

* It does not query the database.
* It can still respond while all database connections are occupied.
* It exposes only total, idle and waiting connection counts.
* It is protected by `CRON_SECRET`.
* It is temporary and marked for removal.

That endpoint should help us distinguish a slow query from a burst of simultaneous requests.

## Corrections before deployment

### 1. Do not push directly to `main`

Replit should not run:

```bash
git push origin main
```

Your Railway repository is a compiled deployment repository, while the source changes are being made in the Replit workspace. Replit should follow the established process:

1. Commit the source change.
2. Rebuild the compiled API bundle.
3. Confirm the generated bundle contains `/api/pool-stats`.
4. Create a narrow PR against the Railway deployment repository.
5. Let you review and merge it.
6. Allow Railway to deploy automatically.

This preserves the audit trail and prevents an unreviewed production change.

### 2. Do not put your personal password in a curl command

Do not run or paste this with your real account:

```bash
-d '{"email":"your@email.com","password":"yourpassword"}'
```

That can leave the password in shell history, logs, screenshots or command output.

For this investigation, the login test can wait until the suspected database route is identified. When login is tested, Replit should either:

* use a dedicated non-admin test account through a secure method, or
* have you test login normally in the app while Replit watches pool counters.

Never send Replit your password in chat.

### 3. The deployment itself should provide the clean baseline

Once the pool-stats PR is merged, Railway will start a new API process. That already creates a fresh pool.

Therefore, the sequence should be:

1. Railway deployment becomes Active.
2. Immediately record `/api/pool-stats`.
3. Begin controlled tests.

Do not add another restart unless the newly deployed process is already exhausted before testing begins.

### 4. Do not share raw SQL from `pg_stat_activity`

The Railway query is useful, but `query_prefix` can contain email addresses, search terms or other user-provided values.

It may be viewed privately in Railway for diagnosis, but Replit’s report to us should provide only:

* query category,
* table names,
* duration,
* state,
* wait event,
* likely route,
* and a sanitized query signature.

No literal values or personal information should be copied into chat.
