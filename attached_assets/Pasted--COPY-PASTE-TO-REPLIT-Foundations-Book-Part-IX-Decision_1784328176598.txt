## 1. Add Part IX to the Foundations Book

**Approved: Yes.**

Add:

# Part IX — Approved Presentation & Asset Registry

This section is necessary because Mapping With Melanin™ now has multiple decks, repeated brand messages, reusable slides, protected language, custom visual assets, and audience-specific variations.

Without a formal registry, we risk:

* inconsistent messaging;
* duplicate or outdated slides;
* different versions circulating;
* accidental edits to protected language;
* one deck being updated while others are forgotten;
* trademark formatting inconsistencies;
* visual drift across presentations.

Part IX should become the governance system for every approved presentation asset.

---

## 2. Track All Approved Decks and Slides With Unique IDs

**Approved: Yes.**

The registry should track every approved deck and every approved slide.

Use unique IDs such as:

```text
MWM-EXP-S01-V1
MWM-INV-S05-V2
MWM-BIZ-S09-V1
MWM-COM-S03-V3
```

The ID system should identify:

* deck;
* slide number;
* version.

Every approved slide record should include:

* exact approved copy;
* visual treatment;
* audience;
* emotional objective;
* source file;
* current deck usage;
* approval date;
* approval status;
* protected or reusable status;
* related speaker notes;
* legal or factual review requirements.

Draft or unapproved slides should be clearly marked and should not be treated as part of the approved registry.

---

## 3. Make Controlled Propagation a Permanent Standard

**Approved: Yes.**

Controlled propagation should become permanent.

When a master slide, approved message, design token, icon, or reusable component changes, Replit must:

1. audit every related deck and file;
2. identify affected slides and variations;
3. explain the impact;
4. distinguish exact copies from audience-specific adaptations;
5. identify decks that should not change;
6. present an Impact Report;
7. ask whether to update:

   * all affected decks;
   * selected decks;
   * or only the current deck;
8. wait for explicit authorization;
9. implement only the approved scope;
10. verify every changed deck;
11. update the registry and changelog.

No automatic cross-deck changes should occur.

Positive feedback about a master change does not authorize propagation.

The explicit cross-deck implementation phrase remains:

> **Please implement this approved master-slide update across every registered deck that uses it.**

Without that authorization, update only the specifically named deck.

---

## 4. Preserve Archived Slide Versions

**Approved: Yes.**

Previous approved versions must remain accessible and should never be permanently overwritten.

Each archived version should retain:

* slide ID;
* version number;
* date approved;
* date replaced;
* reason for the change;
* approved copy;
* visual preview;
* source file or component;
* decks where it appeared;
* person who approved it;
* legal or factual status where relevant.

Archived versions should be clearly labeled:

* Current
* Superseded
* Archived
* Draft
* Rejected

Only the current approved version should be used in active presentations unless an older version is explicitly restored.

This archive is especially important for:

* legal history;
* trademark-sensitive wording;
* investor communications;
* documentary history;
* brand evolution;
* determining what was publicly presented at a specific point in time.

---

## 5. Include Internal Metadata in Every Deck File

**Approved: Yes, with one condition.**

Internal metadata should be included in every deck file, but it should not appear visibly to the audience unless intentionally included.

The metadata should live in one or more of the following:

* hidden slide;
* notes section;
* internal appendix;
* file metadata;
* deck manifest;
* source-code configuration;
* internal-only footer layer that is excluded from exports.

Each deck should record:

```text
Foundations Book Version:
Storytelling Standards Version:
Color System Version:
Typography System Version:
Iconography Version:
Slide Registry Version:
Deck Version:
Last Synchronized:
Approval Status:
Owner:
Confidentiality:
```

Example:

```text
Foundations Book: v1.0
Storytelling Standards: v1.0
Color System: v1.1
Typography System: v1.0
Slide Registry: v1.0
Deck: Experience Deck v1.3
Last synchronized: July 2026
Approval status: Approved
Owner: Founder
Classification: Internal Master / Public Presentation
```

This metadata is for governance and version control.

It should not clutter the visible presentation or appear in public exports unless explicitly requested.

# Additional Required Rule — Exact vs. Adapted Slides

The registry must distinguish between:

## Exact Master Slide

The slide matches the approved master copy and design.

## Audience Adaptation

The slide is based on the master but intentionally adjusted for a specific audience.

## Related Concept

The slide covers the same idea but is not governed as a direct copy.

This distinction is necessary so controlled propagation does not accidentally overwrite appropriate audience-specific storytelling.

---

The audit and propagation system should also cover:

* approved copy;
* mission and vision language;
* founder biography;
* product descriptions;
* KinfolkAI™ descriptions;

* Founding Community terminology;
* trademark formatting;
* custom gold outline icons;
* colors;
* typography;
* screenshots;
* photography;
* speaker notes;
* legal and factual claims;
* Zoom messaging;
* email language;

A change to a protected brand message should trigger an audit of every place where that message appears.

It should never trigger an automatic edit.
