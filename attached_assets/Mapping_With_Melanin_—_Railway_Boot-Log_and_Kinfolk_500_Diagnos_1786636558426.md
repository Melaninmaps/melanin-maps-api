## What is directly wrong in the startup design

The deployed server opens its HTTP port and then begins these asynchronous background operations at the same time:

```ts
initStripe().catch((err) => logger.error({ err }, "Background Stripe init failed"));

runStartupMigrations(logger)
  .then(() => { /* start dependent scheduler */ })
  .catch(/* ... */);
```

The log sequence confirms that the application declares itself ready while schema tasks and StripeSync are still racing. This design lets the service accept member traffic before required boot work has reached a verified state and lets some migration failures continue as if they were harmless.

## Surgical repair order

### 1. Do not guess the Kinfolk root cause

Retrieve the **post-475872f2** log generated by the confirmed smoke test at approximately 2026-08-13 15:54 UTC:

```text
POST /api/kinfolk/chat
message: What is 2 plus 2?
result: HTTP 500, code KINFOLK_ERROR
```

Required sanitized output:

```text
[kinfolk-chat-error] code=... providerStatus=... errName=... is401=... isConnRefused=... active=... queued=... msg=... stack=...
```

The stack fragment must identify the exact failing expression. No credentials, cookies, prompts beyond the test prompt, or member identifiers may be included.

### 2. Make migration status authoritative

Replace best-effort logging for **required** migrations with a readiness gate. The application may listen for Railway health checks, but `/api/readyz` must return `503` until required migrations pass. It must report the specific failing migration ID—not a false `ok` state.

Required migrations include any table/column read in the authenticated Kinfolk chat path, as well as the Library resolver dependencies.

### 3. Fix the StripeSync schema defect independently

Do not attempt to cure the chat 500 by disabling Stripe wholesale. First make the Stripe migration completion check real:

```ts
await runMigrations({ databaseUrl });
const { rows: [{ exists }] } = await pool.query<{ exists: boolean }>(
  `SELECT to_regclass('stripe.accounts') IS NOT NULL AS exists`,
);
if (!exists) {
  throw new Error('StripeSync migration did not create stripe.accounts');
}
```

Only after that check may `getStripeSync()` or `findOrCreateManagedWebhook()` execute. If the check fails, Stripe should be marked unavailable in readiness diagnostics and the webhook setup must be skipped; routine member browsing must not fail.

### 4. Repair Kinfolk cultural-document migrations as one ordered unit

The `kinfolk_cultural_documents` table must be created before any foreign key, embedding, index, or trigger migration refers to it. Inspect the entity key type on both sides of the foreign key; use the same UUID/text type and collation. Existing duplicate entity canonical names must be deterministically remediated before recreating the unique index, with a dry-run report and an explicit winner rule.

### 5. Add a real member-path readiness test

A green provider probe is insufficient. Create a `POST /api/internal/kinfolk-chat-smoke` endpoint protected by `x-cron-secret` that uses no real user data, no persistent chat session, and a fixed `What is 2 plus 2?` test. It must exercise the same prompt construction and model call as member chat. The response may contain only `{ok, status, code, latencyMs, deploymentSha}`.

The boot log gives a credible reason to halt launch certification: the application is reporting real failed migrations while continuing to claim readiness. It is evidence of unsafe operational behavior, but it is **not yet the exact Kinfolk stack trace**. The requested sanitized `[kinfolk-chat-error]` record remains the shortest path to the precise code-line repair.
