2.2 Fix 2 — iOS heritage marker isolation + TDZ crash fix — `artifacts/mobile/components/FullMapView.tsx`
Marker isolation (the prime native-crash suspect from the audit). The `Platform.OS === "android" ? plainCircle : viewWithFeatherIcon` branch inside the heritage `<Marker>` was replaced with an unconditional plain circle. Expo SDK 57 makes Fabric mandatory on both platforms; the crash class that forced the Android isolation (view-recycling SIGSEGV when markers contain Text/icon children) exists identically on iOS, and up to 250 such markers mount and recycle during pan/zoom. Selection feedback is preserved via the existing size-change style (`culturalMarkerSelected`) and the selection card. Icon restoration remains gated on crash-logger evidence, exactly as the Android comment already specified.

TDZ crash fix. The auto-fit `useEffect` (lines 172–188 on `main`) referenced `mapped` twenty-two lines before `const mapped = businesses.filter(…)` — a temporal-dead-zone error. This is not stylistic: `tsc` fails on it today (TS2448/TS2454 — mobile typecheck was red on `main`), and Hermes throws `ReferenceError` at component mount when the effect closure is created. The effect block was moved below the `mapped` declaration with logic byte-for-byte unchanged. 2.3 Fix 3 — `BusinessMapView` cultural markers — `artifacts/mobile/components/BusinessMapView.tsx`
The same isolation applied to the second map component, which the audit found had the identical Feather-child pattern plus two hardening gaps: the `<View><Feather name="book-open"/></View>` child becomes a plain circle, `tracksViewChanges={false}` is added (it was missing here, unlike FullMapView), and coordinate validation is upgraded from `isNaN`-only to `Number.isFinite` plus latitude/longitude range checks, matching FullMapView:

2.4 Fix 4 — OTA runtime pinning — `artifacts/mobile/app.json` + `docs/OTA-COMPATIBILITY-POLICY.md` (new)
`"runtimeVersion": { "policy": "appVersion" }` became `"runtimeVersion": "1.1.5-native.2"`. Under the old policy, all four live binaries (iOS 97/98, Android VC71/VC73) shared runtime `1.1.5`, so any `eas update` reached all of them simultaneously — and the next binary adds Sentry’s native SDK, making a forward-incompatible OTA a realistic fleet-wide crash event. The explicit `-native.N` suffix increments only when the native surface changes; the new `docs/OTA-COMPATIBILITY-POLICY.md` codifies the rule, the operational consequences (existing binaries are intentionally frozen — safe-by-default), and the founder-gated exception path for emergency JS fixes to the legacy fleet.

2.5 Fix 5 — Security hygiene — `dist/public/mobile-build.zip` removed from tracking
The 14.5 MB mobile app source archive was still git-tracked inside the deployable public asset directory. It currently 404s in production, but any future deploy that serves `dist/public/` statically would re-expose it. Removed via `git rm --cached` in commit `f8845285`.

6. Regression Surface and Risk
The server change is additive (two new JSON fields, one startup hash of a ~19 MB file — a one-time ~50 ms cost, measured locally). The marker isolation removes rendering complexity rather than adding it; the visual change (icon → colored circle) matches what Android testers have already been seeing since VC71 and is explicitly reversible once crash evidence lands. The TDZ move changes no logic. The OTA pin’s only behavioral effect is deliberate: legacy binaries stop receiving updates (§2.4 policy documents the exception path). Typecheck: api-server fully clean; mobile reduced to pre-existing errors only. The one sequencing risk is the OTA-before-merge ordering for fix4 described in §4 — it is called out in bold there because getting it backwards strands the current fleet without the marker fix.
