The revised ordering fixes the original race. The token is now removed **before** `setUser(null)` allows the login screen to mount, so auto-restore cannot immediately recover the old session.

I would approve it with **one final adjustment**: do not make server revocation completely fire-and-forget.

A background `fetch()` in a mobile app is not guaranteed to finish if the app is suspended or closed. That could leave the old server session active until it expires. It would not block the new login, but it weakens the meaning of “Log Out,” especially on a lost or shared device.

Use this balance:

1. Read the current token.
2. Delete both local keys.
3. Clear local user state so the login screen is clean.
4. Attempt server revocation with a **short bounded wait**, such as 2–3 seconds.
5. Never restore the local token if revocation fails.
6. Return cleanly after the deadline.

That keeps logout responsive while making a genuine effort to revoke the server session.
