The evidence is useful, but I would **not yet accept “concurrent startup burst” as proven**.

The sequential tests proved something narrower:

* each individual route is fast,
* each releases its connection,
* no single route alone causes exhaustion,
* there is no obvious simple leak in those four handlers.

That is good progress.

However, with responses around **100–223 ms**, a five-connection pool should normally process 8–12 simultaneous requests in well under 10 seconds. The extra requests would briefly wait, then use connections as the first queries finish. A burst alone should not permanently exhaust the pool unless there is sustained traffic, another app instance, background polling, a database connection problem, or materially slower behavior under concurrency.

## What could still explain it

The next investigation should consider:

* multiple Railway API replicas, each creating its own five-connection pool;
* mobile hooks repeatedly polling or retrying rather than firing only once;
* multiple app screens remaining mounted and fetching simultaneously;
* background cron or monitoring requests;
* connection establishment problems between Railway and the database;
* the production connection string using an unpooled database endpoint;
* traffic from testers, web visitors, or health checks;
* queries becoming much slower only when several run concurrently.

Neon recommends using its pooled connection endpoint for applications that may open many connections, and it now provides pooled-client and pooled-server connection graphs for diagnosing patterns. ([Neon][1])

## One important configuration check

If Railway is using a direct Neon connection instead of the pooled `-pooler` endpoint, that may be contributing. Neon’s official guidance says the pooled endpoint is designed to let many client connections share a smaller set of actual PostgreSQL connections. ([Neon][1])

That does not mean Replit should immediately replace `DATABASE_URL`. First it should report whether the current hostname is classified as pooled or direct and verify compatibility with your database code.

We have ruled out a simple route-level connection leak in the four tested endpoints.

We have **not yet proven** that normal app concurrency alone explains a pool becoming unusable for 30 minutes. The next controlled concurrency and passive-monitoring pass should settle that without exposing testers or production to an aggressive load test.
