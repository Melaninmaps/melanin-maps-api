Choose **Option B: implement Sign in with Apple token revocation before submission**.

Because your goal is not merely to submit quickly—it is to submit quickly **without creating an avoidable rejection risk**. Apple explicitly says apps using Sign in with Apple should revoke the associated tokens when the user deletes an account. ([Apple Developer][1])

Apple’s current technical guidance does provide a fallback when an app did not retain a refresh token, but that fallback still requires deleting the account data, directing the user to manually revoke access, and responding correctly to credential-revoked notifications. It is not simply “delete our database row and address revocation after launch.” ([Apple Developer][2])

## Two corrections to Replit’s report

First, this statement is too confident:

> “Apple’s App Review functional test passes.”

Replit cannot guarantee that. Apple may inspect or test the Sign in with Apple deletion path, and Apple’s published guidance specifically addresses token revocation.

Second, this failure mode is not fully safe:

> Sessions deleted, user deletion fails, mobile stays logged in.

The app would appear signed in locally while its server session was already destroyed. The next request would return 401. That recreates the confusing signed-in/logged-out mismatch you have already spent a week trying to eliminate.

The session deletion and user deletion should be performed in one database transaction wherever feasible:

* both succeed; or
* both roll back.

## Fastest compliant approach

Ask Replit to determine whether a **minimal compliant implementation** can be completed sooner than the estimated two to three days. It needs to use the authorization code supplied by Apple, exchange it server-side for tokens, store the required revocation token securely, and call Apple’s `/auth/revoke` endpoint during account deletion. Apple’s revocation endpoint accepts an access token or refresh token, along with the client ID and generated client secret. ([Apple Developer][3])
