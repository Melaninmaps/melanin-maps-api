This is strong progress, but I would **not publish the OTA or assume PR 3 is live in Railway yet**. There are a few items Replit needs to clarify first.

## What looks correct

The overall architecture is right:

* Polling is tied to map focus, authentication and app activity.
* Polling effects remain unconditionally called, preserving React hook order.
* Cleanup should run when focus, app state or authentication changes.
* Duplicate recurring polling is disabled in `BusinessMapView`.
* The server cache remains separate from the mobile changes.
* No pool-size increase, schema change or broad rewrite was introduced.

## Items that must be resolved before release

### 1. These are described as PRs, but no PR links were provided

Replit appears to have edited all files in one workspace at the same time. We need confirmation that the changes are truly separated into reviewable commits or PRs.

Ask for:

* PR 1 link and exact commit
* PR 2 link and exact commit
* PR 3 link and exact commit
* proof that each contains only its stated files
* clean working-tree status before each OTA or server build

Do not publish an OTA from a working tree that contains all three uncommitted change sets mixed together.

### 2. PR 3 is probably not live in Railway production

The statement:

> “Server deploy — already live on Railway via the api-server workflow restart”

is concerning.

Restarting the Replit API development server does **not** deploy the changed source to Railway. Your Railway production service deploys from the separate compiled GitHub repository.

Replit must:

1. Rebuild `dist/index.mjs`.
2. Confirm the cache code exists in the compiled bundle.
3. Create a separate deployment PR against `Melaninmaps/melanin-maps-api`.
4. Have you merge it.
5. Confirm Railway deployed that commit.
6. Test the production endpoint afterward.

Until that happens, treat the proximity cache as **not live in production**.

### 3. Confirm exactly how `isFocused` is being calculated

The report says `FullMapView` uses `useFocusEffect` to derive `pollingEnabled`, but it does not show the implementation.

It should use a safe pattern such as setting focused state on focus and clearing it in the focus-effect cleanup. Replit needs to provide the exact code because an incorrect callback dependency could repeatedly toggle the polling effect or create extra starts and stops.

Also confirm that `useCallback` is imported from **React**, not from `expo-router`. `useFocusEffect` may come from `expo-router`, but React’s `useCallback` should ordinarily come from `react`.

### 4. PR 2 should remove the hooks, not merely leave disabled copies without explanation

Calling:

```ts
useActivityAlerts({ enabled: false });
useSafetyProximity({ enabled: false });
```

is acceptable as a minimal temporary measure because it preserves hook order, but it still initializes hook-level state and AppState listeners unless the hooks are carefully structured.

Replit should confirm:

* no timer is created,
* no location subscription is created,
* no initial fetch runs,
* no AppState listener is registered unnecessarily when permanently disabled,
* and no DB request occurs from `BusinessMapView`.

The device observation after OTA is the deciding proof.

### 5. The mobile typecheck did not fully pass

“Zero new errors” is not the same as a clean production build check.

Before OTA publication, Replit should run an Expo export/bundle validation for iOS. A successful JavaScript bundle generation is especially important because the full TypeScript check still contains known errors.
