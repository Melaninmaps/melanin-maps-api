Yes — this is enough evidence to approve the fix path.

The device test confirmed the issue is real, repeatable, and caused by mobile polling lifecycle behavior:

* polling continues after leaving the Map tab,
* continues while the app is backgrounded,
* continues after logout,
* and duplicates when a business profile map opens.

A single tester can push the 5-connection pool to its limit. Two testers could cause login, Community, Events, businesses, and map data to fail again.

## Approve these three PRs

### PR 1 — Mobile polling lifecycle fix

This should include, in one focused PR:

* poll only while the Map tab is focused,
* pause when the app is backgrounded or inactive,
* stop polling when the user logs out,
* prevent overlapping polling cycles,
* apply the same lifecycle protections to both:

  * `useActivityAlerts`
  * `useSafetyProximity`

Acceptance criteria:

* Open Map: polling starts.
* Leave Map: polling stops.
* Background app: polling stops.
* Return to Map: polling resumes once.
* Logout: polling stops completely.
* No duplicate intervals.
* `waitingCount` stays at zero.

### PR 2 — Remove duplicate BusinessMapView polling

The business detail map should not independently mount the same continuous polling hooks.

Smallest safe launch fix:

* remove recurring `useActivityAlerts` and `useSafetyProximity` polling from `BusinessMapView`,
* load any necessary data once on screen open,
* or use already available parent/shared data,
* preserve cleanup behavior.

Acceptance criteria:

* Opening a business profile does not increase sustained pool usage.
* Closing the profile returns to baseline.
* Business map still displays correctly.
* No loss of necessary safety or alert information.

### PR 3 — Server protection for proximity warnings

Keep this separate.

Before adding indexes, use the proven immediate safeguards:

* short-lived cache for identical or near-identical coordinate requests,
* reject overlapping duplicate requests where practical,
* preserve the current route response,
* do not increase pool size yet.

Indexes can follow after query-plan evidence is available.

Acceptance criteria:

* repeated requests for the same nearby coordinates use the cache,
* route remains under 1 second while the pool is healthy,
* no user-specific data leaks between cache entries,
* cache expires promptly,
* no change to response format.
