Q5. Confirm authentication token behavior.

─────────────────────────────────────────────────────────────────────



  EXPIRATION

    SESSION_TTL = 7 days from creation.

    Stored as an expire timestamp in the sessions table.



  VALIDATION

    Server-side on every authenticated request.

    Reads session row → checks expire timestamp → deletes and

    rejects if expired. No client-side trust of any kind.



  LOGOUT INVALIDATION

    POST /api/mobile-auth/logout reads the Bearer token from the

    Authorization header, then calls deleteSession(sid) which

    issues a DELETE against the sessions table row. The token is

    permanently invalid from that moment. The same endpoint is

    used by the web app's clearWebToken() function.



  REFRESH BEHAVIOR

    None. There is no token refresh or sliding expiration.

    Sessions that are used within the 7-day window do NOT have

    their expiry extended automatically. A user inactive for

    7 days will need to sign in again. This behavior is

    inherited from the existing mobile session design and was

    not changed.



─────────────────────────────────────────────────────────────────────

Q6. Is localStorage used only as a session token store, or are

    any sensitive credentials stored there?

─────────────────────────────────────────────────────────────────────



ONLY the session token is stored. Key: "web_auth_token".



  The value is a randomly-generated session ID (opaque string,

  not a JWT, contains no user data, no password, no PII).

  It is a server-side session reference only — meaningless

  without a live matching row in the sessions table.



  No passwords, reset codes, email addresses, personal data,

  API keys, or other credentials are written to localStorage

  by any of the new authentication code.



  Known security characteristic: localStorage is accessible

  to any JavaScript running on the same origin, making it

  less resistant to XSS than an HttpOnly cookie. This is an

  accepted tradeoff given that the native login routes return

  a JSON body token (not a Set-Cookie header), and the backend

  was not modified. The same tradeoff exists in the current

  mobile implementation using SecureStore.
