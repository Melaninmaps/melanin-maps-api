## Important checks before deployment

### 1. Confirm which production database Railway actually uses

The report suddenly refers to a **Neon production database**. Earlier, your production database was described as Railway PostgreSQL. Do not run any schema command until Replit proves the exact database host used by Railway’s current `DATABASE_URL`.

Ask for a sanitized response showing only:

* provider/hostname;
* database name;
* whether the `users` table exists there;
* whether `apple_refresh_token` already exists.

Do not allow them to expose the password or complete connection string.

### 2. Prefer an automatic, idempotent production migration

Rather than having you manually connect to Neon and type SQL, the Railway deployment should safely execute:

```sql
ALTER TABLE users
ADD COLUMN IF NOT EXISTS apple_refresh_token TEXT;
```

This must happen **before the new server bundle begins accepting Apple sign-ins**. Otherwise, the new code could deploy while the column is missing, causing production failures.

### 3. Verify the Apple revocation URL

Apple’s Sign in with Apple endpoint is:

```text
https://appleid.apple.com/auth/revoke
```

Apple requires the request to include the correct `client_id`, client-secret JWT, token and token type hint. A successful revocation returns HTTP 200 with no required response body. ([Apple Developer][2])

Have Replit confirm that `apple.ts` uses that exact endpoint—not Apple’s separate organizational-data-sharing endpoint.

### 4. Existing-user fallback needs careful interpretation

Allowing an existing Apple user to sign in when token exchange fails can be acceptable as a temporary legacy compatibility path, but the system must not confuse:

* a truly legacy user who has no stored token; and
* a current user whose exchange failed because production is misconfigured.

At minimum, structured logs should distinguish:

```text
APPLE_TOKEN_EXCHANGE_LEGACY_NO_CODE
APPLE_TOKEN_EXCHANGE_CONFIGURATION_ERROR
APPLE_TOKEN_EXCHANGE_APPLE_REJECTED
APPLE_TOKEN_EXCHANGE_NETWORK_ERROR
```

No authorization code, token or private-key data should be logged.

### 5. Credential-state checking is appropriate

Apple says a revoked credential should result in the user being signed out, and `notFound` means the Apple relationship no longer exists. Checking the stored Apple user ID when the app becomes active is therefore directionally correct. ([Apple Developer][3])

Replit should also confirm that:

* this check runs only for Apple users;
* temporary Apple API errors do **not** automatically log the user out;
* `transferred` is not treated as revoked;
* SecureStore cleanup happens on manual logout, deletion and revoked status.
