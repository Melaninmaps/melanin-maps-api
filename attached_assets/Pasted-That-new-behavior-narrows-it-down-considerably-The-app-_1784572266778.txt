That new behavior narrows it down considerably.

The app is successfully restoring a valid saved session after a full close, but **logout is not leaving the authentication state clean enough for a fresh login**. This is no longer primarily an app-resume problem.

Most likely, logout is clearing only one credential while another remains, or the login screen is still using stale auth state after logout. For example:

* secure-storage token cleared, but an auth cookie remains;
* cookie cleared, but local token remains;
* server session revoked, but the client still thinks the old session is active;
* logout finishes, but cached user/auth queries are not reset;
* login immediately races with an unfinished logout request.

## About “auto open”

You are right that users should control this.

I would separate two choices:

**Keep me signed in**
Keeps the session available after closing and reopening the app.

**Open directly to my account**
Skips the welcome/sign-in screen when a valid saved session exists.

A secure default would be:

* “Keep me signed in” offered during login and clearly explained.
* Default **off** on shared or public devices.
* The user can change it later under **Settings → Privacy & Security**.
* Even when enabled, sensitive areas such as payments, identity verification, or admin access can require Face ID, Touch ID, or the password again.

This should not create a new user ID or separate account. It only controls session convenience.
