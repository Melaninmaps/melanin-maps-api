This backlog is organized well, but I would **not approve LB-009 as only “max: 5 + two timeouts” yet**. That is directionally correct, but it is not enough by itself to prove the system is safe for 50–500 users.

A few important points:

* `pg` already defaults to a maximum pool size of 10. Setting `max: 5` lowers concurrency; that may be appropriate, but Replit should justify it against the actual production database limit, Railway instance count, and expected traffic rather than choosing it arbitrarily. ([Node Postgres][1])
* `statement_timeout` and `query_timeout` are valid `pg` client options and would prevent individual statements or query calls from running forever. ([Node Postgres][2])
* If production truly uses Neon, the normal application connection should generally use Neon’s pooled hostname containing `-pooler`; direct connections are better reserved for migrations and administrative work. ([Neon][3])

## What I recommend now

Approve LB-009 as a **small, staged server-resilience package**, not as one unverified change.

### Batch 9A — Prevent indefinite hangs

This should be implemented first:

* finite connection timeout;
* `statement_timeout`;
* `query_timeout`;
* explicit pool maximum;
* structured logging when a timeout occurs;
* guaranteed error response instead of an endless request.

This is server-only and should not require another mobile build.

### Batch 9B — Correct API behavior during DB trouble

The server should return:

```text
503 Service temporarily unavailable
```

for database timeout or pool saturation—not `500`, and not “invalid email or password.”

The mobile app should receive enough information to display:

> We’re having trouble connecting right now. Your account is safe. Please try again shortly.

### Batch 9C — Confirm the connection architecture

Before changing the connection string:

* prove whether the live production hostname is Railway Postgres or Neon;
* if Neon, confirm whether it contains `-pooler`;
* preserve a separate direct URL for migrations;
* do not run migrations through a pooled transaction-mode URL unless the migration tooling explicitly supports it. Neon specifically recommends direct connections for migrations in most ORM workflows. ([Neon][3])

### Batch 9D — Protect login

Add:

* account/IP rate limiting;
* duplicate-login request suppression;
* one request in flight per device;
* bounded client timeout;
* no automatic aggressive retry;
* pool and endpoint monitoring.
