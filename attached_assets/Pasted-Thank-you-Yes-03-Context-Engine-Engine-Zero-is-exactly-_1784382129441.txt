# 03. CONTEXT ENGINE™

## Future-State Production Specification v1.0

**Classification:** Foundational Context-Resolution Engine
**Status:** Review Mode — designed as the launch-state model
**Confidentiality:** Highest restriction; context-detection signals, resolution logic, priority rules, confidence calculations, and engine-routing instructions are confidential trade secrets and are not publicly disclosed

---

## 03.1 Purpose

The Context Engine™ determines the circumstances under which a Mapping With Melanin™ decision is being requested.

It is designated **Engine Zero** because no other intelligence engine may be interpreted correctly until the relevant context has been identified.

The same business, neighborhood, event, resource, opportunity, Cultural Ambassador, or community experience may be appropriate in one context and inappropriate in another.

For example:

* a restaurant may be suitable for a daytime family gathering but not for a solo traveler late at night;
* a neighborhood may be appropriate for a short visit but not yet sufficiently supported for relocation;
* an emerging business may be discoverable but not eligible for active promotion;
* an event may be culturally relevant but unsuitable for a user’s accessibility requirements;
* a resource may be geographically relevant but unavailable to the user because of eligibility restrictions;
* a Cultural Ambassador may be appropriate for local storytelling but not for a safety-sensitive recommendation;
* an urgent safety request must not be processed using ordinary discovery weights.

The Context Engine™ determines:

1. what the user is trying to accomplish;
2. who or what the request concerns;
3. where the request applies;
4. when the request applies;
5. what conditions materially affect the decision;
6. which context profile governs the request;
7. whether multiple contexts must be evaluated;
8. which engines must participate;
9. which engine should lead;
10. which minimum thresholds and override rules apply;
11. how confident the platform is that it has interpreted the request correctly;
12. whether clarification or human review is required.

The Engine’s governing question is:

> **What is happening, for whom, under what conditions, and which decision framework must govern the platform’s response?**

---

# 03.2 Foundational Principle

Context is not a demographic assumption.

The Context Engine™ must not infer a person’s identity, vulnerability, intentions, family status, disability, income, cultural affiliation, or safety needs solely from appearance, location, browsing history, name, device, or generalized population data.

Context must be established through one or more of the following:

1. explicit user statements;
2. active user selections;
3. current request language;
4. authorized profile preferences;
5. session behavior directly related to the request;
6. verified location and time conditions;
7. known entity characteristics;
8. applicable safety or governance conditions;
9. system events requiring a mandatory context;
10. cautious inference supported by multiple independent signals.

The Context Engine™ may infer operational circumstances.

It may not convert those circumstances into unsupported conclusions about the person.

For example:

```text
Allowed:
The user requested directions at 11:45 PM and selected “traveling alone.”
Apply the Solo Traveler + Night Safety context.

Not allowed:
The user is a woman in an unfamiliar neighborhood.
Assume she is traveling alone and afraid.

Allowed:
The user selected wheelchair accessibility as a required preference.
Apply the Accessibility Required modifier.

Not allowed:
The user viewed an accessible venue.
Assume the user has a disability.
```

# 03.3 Definition of Context

For Mapping With Melanin™, **context** is the structured description of the circumstances that materially change how evidence must be interpreted or how a decision must be made.

A context is composed of six layers:

```text
Intent
+ Subject
+ Person or Audience
+ Place
+ Time
+ Conditions
= Resolved Context
```

# 03.5 Decision Modes

Context and decision mode are separate.

The same context may produce different results depending on what the platform is being asked to do.

| Decision mode | Meaning                                                                                   |
| ------------- | ----------------------------------------------------------------------------------------- |
| `SEARCH`      | Return relevant matching results                                                          |
| `INFORM`      | Provide factual or educational information                                                |
| `COMPARE`     | Compare two or more entities or options                                                   |
| `RECOMMEND`   | Identify options suitable for a stated context                                            |
| `PROMOTE`     | Actively elevate, feature, sponsor, or amplify an entity                                  |
| `RECOGNIZE`   | Award or display a badge, milestone, status, or distinction                               |
| `ALERT`       | Warn users about a credible concern                                                       |
| `ROUTE`       | Direct a request, report, or person to the correct destination                            |
| `VERIFY`      | Determine whether an entity, claim, report, or credential meets verification requirements |
| `MODERATE`    | Evaluate platform content or conduct                                                      |
| `ESCALATE`    | Send a decision for human, legal, safety, or governance review                            |
| `LEARN`       | Record an outcome for future system improvement without changing a public result          |

A `SEARCH` result does not automatically qualify for `RECOMMEND`.

A `RECOMMEND` result does not automatically qualify for `PROMOTE`.

A `PROMOTE` result does not automatically qualify for permanent `RECOGNIZE` status.

# 03.6 Urgency Levels

Each request receives an urgency classification.

| Level | Name           | Meaning                                          | Maximum automated delay |
| ----: | -------------- | ------------------------------------------------ | ----------------------: |
|     0 | Routine        | No immediate deadline or risk                    |     Standard processing |
|     1 | Time-sensitive | Availability, event, travel, or deadline matters |              60 seconds |
|     2 | Priority       | Material opportunity or safety concern           |              15 seconds |
|     3 | Urgent         | Credible near-term harm or severe disruption     |               5 seconds |
|     4 | Emergency      | Immediate threat or emergency assistance request |       Immediate routing |

Urgency does not prove that a claim is true.

It determines how quickly the platform must respond and which safeguards must activate.

# 03.7 Context Evidence Sources

The Context Engine™ may use the following evidence sources.

## Tier 1 — Explicit evidence

Highest priority:

1. direct user statement;
2. active user-selected filter;
3. selected task or workflow;
4. verified form field;
5. current emergency action;
6. administrator-selected review category.

## Tier 2 — Authorized profile evidence

Used only when relevant and permitted:

1. saved travel preferences;
2. accessibility preferences;
3. family-plan configuration;
4. selected cultural interests;
5. saved safety preferences;
6. preferred transportation mode;
7. saved budget settings;
8. business or Cultural Ambassador role.

## Tier 3 — Current-session evidence

May supplement but not override explicit input:

1. search terms;
2. currently viewed category;
3. selected map region;
4. destination;
5. route request;
6. time of request;
7. recently applied filters;
8. sequence of related actions.

## Tier 4 — Environmental evidence

Used cautiously:

1. verified local time;
2. business operating hours;
3. route conditions;
4. active platform safety alert;
5. weather-related disruption;
6. event schedule;
7. public emergency notice;
8. geographic service availability.

## Tier 5 — Inferred evidence

Lowest priority and never sufficient alone for sensitive contexts:

1. likely intent inferred from multiple session actions;
2. probable trip stage;
3. likely comparison objective;
4. probable geographic scope;
5. likely need for clarification.

Inferred context may not independently activate:

* emergency status;
* child status;
* disability status;
* protected identity;
* financial hardship;
* discrimination victim status;
* family status;
* criminal suspicion;
* immigration status;
* medical condition.

# 03.8 Context Detection Sequence

Every consequential request passes through the following sequence:

```text
1. Receive Request
2. Identify Decision Mode
3. Extract Explicit Intent
4. Identify Subject Entity
5. Identify Person or Audience
6. Resolve Geographic Scope
7. Resolve Timeframe
8. Apply Explicit Conditions
9. Retrieve Authorized Preferences
10. Evaluate Current-Session Signals
11. Check Mandatory Safety or Governance Contexts
12. Generate Candidate Contexts
13. Score Candidate Contexts
14. Resolve Primary Context
15. Assign Secondary Contexts
16. Apply Modifiers
17. Calculate Context Confidence
18. Determine Engine Participation
19. Determine Engine Leadership
20. Apply Threshold Profile
21. Request Clarification or Continue
22. Write Context Audit Record
```

No final BIF score may be calculated until Steps 1–20 are complete.

Emergency routing may begin before the full sequence is complete when delay could create harm.

# 03.9 Candidate Context Scoring

Each possible context receives a **Context Applicability Score** from 0 to 100.

## 03.9.1 Formula

```text
Context Applicability Score =
    Explicit Intent Match
  + Workflow Match
  + Subject Match
  + Audience Match
  + Place and Time Match
  + Modifier Match
  + Session Continuity Match
  + Mandatory Rule Adjustment
  - Contradiction Penalty
```

The score is normalized to 0–100.

## 03.9.2 Baseline component weights

| Component                    | Maximum points |
| ---------------------------- | -------------: |
| Explicit Intent Match        |             25 |
| Workflow Match               |             15 |
| Subject Match                |             10 |
| Audience Match               |             10 |
| Place and Time Match         |             10 |
| Modifier Match               |             10 |
| Session Continuity Match     |             10 |
| Mandatory Rule Adjustment    |             10 |
| **Maximum before penalties** |        **100** |

Contradiction penalties are applied after the positive components.

---

## 03.9.3 Explicit Intent Match

| Evidence                                         | Points |
| ------------------------------------------------ | -----: |
| User explicitly selects named context            |     25 |
| User directly states purpose in natural language |     22 |
| User enters through a context-specific workflow  |     18 |
| Intent strongly implied by current request       |     12 |
| Intent weakly inferred                           |      5 |
| No usable intent evidence                        |      0 |

---

## 03.9.4 Workflow Match

| Workflow condition                                | Points |
| ------------------------------------------------- | -----: |
| Request originated inside dedicated workflow      |     15 |
| Request originated through specialized filter set |     12 |
| Request originated from related entity page       |      8 |
| General search with contextual language           |      5 |
| No workflow signal                                |      0 |

Examples:

* opening “Know Before You Move” strongly supports `CTX-RELOCATION`;
* selecting “Report a Safety Concern” strongly supports `CTX-REPORT`;
* opening “Resources Near Me” supports `CTX-RESOURCE`;
* selecting “Find Melanated-Owned Businesses” supports `CTX-MELANATED-OWNED`.

---

## 03.9.5 Contradiction Penalties

| Contradiction                                     | Penalty |
| ------------------------------------------------- | ------: |
| Explicit user rejection of context                |    −100 |
| Context conflicts with selected workflow          |     −30 |
| Context conflicts with subject type               |     −20 |
| Context conflicts with verified time or location  |     −15 |
| Context depends only on prohibited inference      |     −50 |
| Context conflicts with another explicit condition |     −20 |
| Context is unsupported by current evidence        |     −10 |

A score may not fall below zero.

# 03.10 Context Confidence

The Context Engine™ returns a Context Confidence Score from 0 to 100 and a confidence label.

## 03.10.1 Formula

```text
Context Confidence Score =
(
  Signal Strength
  × Signal Agreement
  × Evidence Independence
  × Context Specificity
)
× 100
```

Each component ranges from `0.00` to `1.00`.

---

## 03.10.2 Signal Strength

| Strength                                             | Factor |
| ---------------------------------------------------- | -----: |
| Direct explicit selection                            |   1.00 |
| Direct natural-language statement                    |   0.95 |
| Dedicated workflow                                   |   0.90 |
| Authorized profile preference plus current relevance |   0.80 |
| Multiple current-session signals                     |   0.70 |
| Single inferred signal                               |   0.40 |
| No usable signal                                     |   0.00 |

## 03.10.3 Signal Agreement

| Agreement                  | Factor |
| -------------------------- | -----: |
| All material signals agree |   1.00 |
| Minor ambiguity            |   0.90 |
| One meaningful conflict    |   0.75 |
| Multiple conflicts         |   0.50 |
| Direct contradiction       |   0.00 |

## 03.10.4 Evidence Independence

| Independence                               | Factor |
| ------------------------------------------ | -----: |
| Three or more independent evidence sources |   1.00 |
| Two independent sources                    |   0.90 |
| One direct source                          |   0.80 |
| Multiple signals from the same action      |   0.60 |
| Pure inference                             |   0.35 |
| No evidence                                |   0.00 |

## 03.10.5 Context Specificity

| Specificity                                          | Factor |
| ---------------------------------------------------- | -----: |
| Intent, person, place, time, and conditions resolved |   1.00 |
| One noncritical field missing                        |   0.90 |
| Two noncritical fields missing                       |   0.75 |
| One critical field missing                           |   0.55 |
| Multiple critical fields missing                     |   0.30 |
| Context cannot be meaningfully resolved              |   0.00 |

---

## 03.10.6 Context confidence labels

|  Score | Confidence |
| -----: | ---------- |
| 90–100 | Verified   |
|  80–89 | High       |
|  65–79 | Moderate   |
|  45–64 | Emerging   |
|  20–44 | Low        |
|   0–19 | Unknown    |

# 03.12 Primary Context Selection

The primary context is the context that most directly governs:

1. which engines lead;
2. which weights apply;
3. which thresholds apply;
4. what explanation is appropriate;
5. what risks must be considered;
6. whether the platform may proceed automatically.

The highest Applicability Score does not always become the primary context.

The Engine must also consider:

* mandatory context precedence;
* decision mode;
* urgency;
* explicit user intent;
* safety implications;
* governance restrictions;
* material consequences of being wrong.

# 03.13 Secondary Context Assignment

A candidate context becomes secondary when:

```text
Applicability Score ≥ 55
and
it materially changes engine weights, thresholds, eligibility, or explanation
and
it does not conflict with the primary context
```

Secondary contexts may:

* increase an engine’s influence;
* introduce a minimum threshold;
* add a modifier;
* require additional evidence;
* restrict promotion;
* alter ranking;
* require clarification;
* change the public explanation.

Secondary contexts may not:

* override an emergency rule;
* remove a safety minimum;
* bypass governance;
* reduce an explicit user requirement;
* convert low confidence into verified confidence.

# 03.14 Context Conflict Resolution

Context conflict exists when two valid context candidates would produce materially different decisions.

Examples:

* the user requests a “Hidden Gem” while also requiring extensive verified evidence;
* a venue is highly culturally significant but has unresolved safety reports;
* a user asks for an immediate recommendation but the relocation context requires deeper evidence;
* the user requests a family-friendly option while current event restrictions exclude minors;
* a business is relevant for discovery but ineligible for promotion.

The Context Engine™ applies the following conflict rules.

## Rule 1 — Explicit intent controls ordinary inference

A direct user statement overrides inferred session intent unless a mandatory safety or governance rule applies.

## Rule 2 — Safety-sensitive context controls convenience context

Safety, emergency, and incident-reporting contexts take precedence over general exploration, discovery, promotion, and convenience.

## Rule 3 — Higher-consequence context controls lower-consequence context

Relocation requires more durable evidence than a temporary visit.

Promotion requires stronger evidence than search.

Recognition requires more sustained evidence than a single recommendation.

## Rule 4 — Specific context controls general context

`Solo Traveler at Night` controls `Solo Traveler`.

`Relocation with Family` controls `General Relocation`.

`Verified Melanated Diaspora-Owned Business` controls `General Local Business`.

## Rule 5 — Restrictive explicit requirements remain active

An explicit requirement such as wheelchair accessibility, open now, verified ownership, or child suitability may not be silently removed to increase result volume.

## Rule 6 — Unknown does not equal negative

Missing context evidence does not prove that an option is unsuitable.

It may reduce recommendation eligibility or trigger clarification.

## Rule 7 — Multiple high-consequence contexts require compound evaluation

When two high-consequence contexts apply, the Engine may create a compound context rather than forcing one into a secondary role.

Example:

```text
CTX-RELOCATION-FAMILY
CTX-SOLO-NIGHT-SAFETY
CTX-RESOURCE-URGENT
CTX-AMBASSADOR-PARTNERSHIP
```

## Rule 8 — Unresolvable conflict requires clarification or review

The platform must not invent a preference merely to complete a decision.

| ------------------------- | ----------------------------------------- |
| Solo Night Safety         | Solo Traveler + Nighttime + Safety        |

| Heritage Travel           | Travel + Cultural Heritage                |

# 03.16 Context Clarification Rules

The platform must request clarification when:

1. no context reaches an Applicability Score of 70;
2. the top two contexts are within 8 points and would materially change the result;
3. Context Confidence is below 45 for a consequential recommendation;
4. a required person, place, time, or condition is missing;
5. an explicit user statement conflicts with an active filter;
6. a safety-sensitive request is ambiguous;
7. an accessibility requirement appears relevant but is not confirmed;
8. a recommendation could create substantial financial, legal, relocation, or safety consequences;
9. a user’s request could reasonably refer to multiple geographic locations;
10. the system would otherwise rely on a prohibited inference.

Clarification should be limited to the smallest question necessary.

Examples:

```text
Are you looking for a place to visit, or are you considering moving there?
```

```text
Should I prioritize places suitable for children?
```

```text
Are you looking for options that are open now or later tonight?
```

```text
Do you want only verified melanated diaspora-owned businesses, or should I
also include community-recommended businesses awaiting verification?
```

---

# 03.17 Missing Context Handling

When context is incomplete, the Engine must not fabricate missing values.

It may use one of four responses.

## Response A — Proceed cautiously

Allowed when missing information is unlikely to materially change the result.

## Response B — Provide multiple pathways

Used when two interpretations are both reasonable.

Example:

```text
For visiting:
[results]

For relocation:
[results requiring deeper evidence]
```

## Response C — Ask one clarification question

Used when a single missing fact controls the decision.

## Response D — Hold or escalate

Required when proceeding could create material safety, legal, governance, or reputational harm.


The Context Engine™ must evaluate transitions whenever:

1. the user changes intent;
2. a new location is selected;
3. time conditions materially change;
4. a safety alert activates;
5. a user adds or removes a filter;
6. the subject entity changes;
7. the decision mode changes;
8. new evidence changes the risk level;
9. the user moves from information to action;
10. the user requests promotion, recognition, or verification.

## 03.18.1 Transition preservation rule

The Engine may preserve relevant prior context but must not carry forward obsolete context.

Example:

* accessibility requirements may remain active throughout a travel-planning session;
* a nighttime modifier must expire when the evaluated time changes to daytime;
* an emergency context must end only after the emergency workflow is closed or safely transferred;
* a relocation context should not automatically apply to an unrelated local restaurant search.

# 03.21 Geographic Context Rules

1. user location;
2. searched location;
3. destination;
4. entity location;
5. route;
6. service area;
7. jurisdiction;
8. online or remote availability.

The platform must not assume that the user is physically located in the searched area.

Geographic confidence is categorized as:

| Unknown               | No reliable location                       |

Precise location must be handled according to privacy and permission requirements.

# 03.26 Safety Context Activation

A safety context becomes mandatory when any of the following occur:

1. the user explicitly requests safety information;
2. the user submits or views a relevant incident report;
3. an active Critical or High-Risk safety override exists;
4. the user requests travel or directions under safety-sensitive conditions;
5. a report alleges violence, harassment, discrimination, stalking, threats, or dangerous conditions;
6. a minor’s safety is implicated;
7. the platform detects an urgent emergency action;
8. a route or location is subject to a verified public emergency;
9. a recommendation could expose the user to a known material risk;
10. Governance requires safety review.

Safety context activation must not publicly characterize an entity as unsafe unless the Safety Intelligence Engine™ authorizes the language.

# 03.27 Emergency Context Rules

When `CTX-EMERGENCY` is active:

1. ordinary discovery ranking is suspended;
2. promotional status is irrelevant;
3. paid placement receives zero influence;
4. emergency routing takes priority;
5. the system must avoid unnecessary questions;
6. the platform must clearly state its limitations;
7. relevant emergency resources may be surfaced;
8. location may be requested only when necessary and permitted;
9. the event must be logged;
10. post-event review may be required.

The Context Engine™ does not determine whether an emergency claim is legally proven.

It determines that the request must be handled as potentially urgent until safely resolved.

---

# 03.28 Context Privacy Rules

The Context Engine™ must follow data-minimization principles.

It may use only the context information necessary for the decision.

It must not:

* permanently store temporary sensitive context by default;
* expose private modifiers in public explanations;
* reveal one user’s context to another user;
* infer protected identity for advertising or promotion;
* use precise location without permission;
* convert safety concerns into marketing segments;
* retain emergency context longer than operationally necessary;
* use parent-managed minor context outside authorized workflows;
* expose internal confidence or risk classifications where doing so could cause harm;
* allow paid entities to access private contextual signals.

---

# 03.29 Anti-Manipulation Rules

The Context Engine™ must detect attempts to manipulate context for ranking or eligibility advantages.

Potential manipulation signals include:

1. repeatedly changing context filters to force promotion eligibility;
2. falsely invoking emergency workflows;
3. automated context cycling;
4. mass-generated location requests;
5. attempts to classify paid promotion as organic discovery;
6. business owners impersonating users to create favorable contexts;
7. coordinated use of identical context language;
8. false accessibility claims used to target or exclude users;
9. attempts to bypass ownership verification;
10. deliberate misclassification of an incident report.

Responses may include:

* confidence reduction;
* request throttling;
* reauthentication;
* evidence review;
* promotion hold;
* context lock;
* human moderation;
* governance escalation.

---

# 03.30 Cold-Start Context Rules

The Context Engine™ must operate when little or no personal history exists.

For a new user:

1. rely primarily on the current request;
2. avoid assumptions based on generalized demographics;
3. offer explicit context filters;
4. use baseline weights when context remains general;
5. request clarification only when materially necessary;
6. clearly label unknown suitability;
7. do not penalize the user for having no history;
8. do not silently import context from unrelated sessions.

For a new entity:

1. context may still be resolved;
2. entity confidence may remain low;
3. search may be allowed;
4. recommendation or promotion may require stronger evidence;
5. unknown information must remain unknown.

---

# 03.31 Public Explanation Rules

Public explanations may describe the user-visible reason for a result without revealing internal weights, thresholds, confidence calculations, or proprietary context-resolution logic.

## Approved examples

* “Recommended because it matches your selected family and accessibility preferences.”
* “Shown for your relocation search because community, safety, and resource information is available.”
* “This result is listed, but there is not yet enough verified information for a strong recommendation.”
* “Safety information affected this recommendation.”
* “This business matches your request for verified melanated diaspora-owned options.”
* “We need one more detail before making a recommendation.”

## Prohibited examples

* “The Context Engine assigned a score of 82.”
* “Safety received 35% of the final weight.”
* “Your behavior indicates that you are vulnerable.”
* “We inferred your race, gender, disability, or income.”
* “This result was suppressed because of a confidential algorithm.”
* “The business failed an undisclosed cultural test.”

# 03.37 Institution Test Application

Before a new context, modifier, inference rule, or priority rule is approved, the Governance Engine™ must ask:

> **Would we be willing to explain and defend this context rule as a permanent institutional practice 25 years from now?**

A rule fails the Institution Test when it:

* depends on stereotypes;
* cannot be consistently explained;
* creates hidden discrimination;
* gives commercial interests improper control;
* encourages surveillance;
* cannot be audited;
* becomes harmful when scaled;
* sacrifices dignity for convenience;
* has no correction or appeal pathway.

---

# 03.38 Generational Test Application

The Context Engine™ must also ask:

> **Would this context methodology remain worthy of stewardship if inherited by future generations who did not create it?**

A rule fails the Generational Test when:

* it requires founders’ personal judgment to remain safe;
* it cannot operate transparently under new leadership;
* it encodes temporary bias as permanent truth;
* it prevents future communities from correcting the framework;
* it extracts contextual data without durable benefit;
* it creates power that cannot be governed responsibly.
