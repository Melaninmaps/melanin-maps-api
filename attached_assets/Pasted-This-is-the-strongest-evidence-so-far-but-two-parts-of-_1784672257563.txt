## Two technical corrections

### The matching 30-second timers do not explain `idleCount: 0`

A connection returned to the pool is counted as **idle**, even while it is waiting for `idleTimeoutMillis` to expire.

Therefore:

* `totalCount: 3`
* `idleCount: 0`

does not mean three connections are merely being kept warm between polls. It means, according to the Node pool, all three were checked out at the instant of every sample.

So Replit’s “Scenario B” is not a sufficient explanation.

### `statement_timeout` is not the correct fix for idle transactions

If PostgreSQL shows `idle in transaction`, `statement_timeout` may not terminate that state because no statement is actively running.

The relevant protection is usually:

* fixing the missing commit/rollback first, and
* potentially adding `idle_in_transaction_session_timeout` as a safeguard.

No timeout should be selected until PostgreSQL reports the actual connection states.

## What each PostgreSQL result would mean

| PostgreSQL result                   | Meaning                                                                               |
| ----------------------------------- | ------------------------------------------------------------------------------------- |
| `active`, several seconds or longer | Queries are genuinely running or blocked                                              |
| `idle in transaction`               | A transaction is open and was never completed                                         |
| `idle`                              | PostgreSQL considers connections free; investigate mismatch with Node pool stats      |
| Waiting on `Lock`                   | One query is blocking others                                                          |
| Waiting on client activity          | Server is waiting for the application/client                                          |
| Only one or no production rows      | Pool stats may be coming from multiple processes or behaving differently than assumed |

There is also an important possibility: the pool-stats request may be hitting one Railway instance while other requests hit another. Replica count and instance identity would clarify that.
