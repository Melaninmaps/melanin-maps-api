No—this cannot be allowed to depend on restarting Railway whenever several users retry. Before you grow to 50 or 500 users, the database layer needs **bounded concurrency, bounded query time, and monitoring**.

## What needs to change

### 1. Every database operation must end

A connection timeout only limits how long it takes to establish a new database connection. It does not stop a query that obtained a connection and then hangs.

You need separate limits for:

* acquiring a connection;
* executing a query;
* completing the full HTTP request.

`node-postgres` supports pool connection limits such as `connectionTimeoutMillis`, `idleTimeoutMillis`, and `max`, but these must be sized intentionally. Its pool defaults to a maximum of 10 clients unless configured otherwise. ([Node Postgres][1])

I would require:

* connection-acquisition timeout;
* query/statement timeout;
* request-level AbortController or deadline;
* automatic release or destruction of a client after timeout;
* no route able to wait indefinitely.

### 2. Limit how many requests may consume database connections

The API should not allow every repeated login attempt to occupy another connection indefinitely.

A good production design uses:

* one process-level pool;
* an explicit conservative `max`;
* a short waiting queue;
* fast rejection with `503 Service temporarily unavailable` when the database is saturated;
* rate limits on login and other expensive endpoints;
* client-side protection against duplicate submissions.

Do not simply raise the pool maximum. That may postpone failure while increasing pressure on PostgreSQL.

### 3. Use the correct database connection type

If production truly uses Neon, confirm whether the hostname contains `-pooler`. Neon recommends a pooled connection string for application traffic; its PgBouncer pool allows many client connections to share fewer direct PostgreSQL connections. Direct connections remain appropriate for migrations. ([Neon][2])

The application should generally use:

* **pooled URL** for normal API requests;
* **direct URL** for schema migrations and certain administrative work.

If production is Railway PostgreSQL instead, Neon-specific recommendations do not apply. This is why the canonical database must be proven first.

### 4. Login must be protected at both ends

On the mobile side:

* disable the Sign In button after the first tap;
* prevent duplicate in-flight login requests;
* use a clear timeout;
* allow one deliberate retry;
* do not automatically issue repeated requests;
* never erase valid credentials because of a 5xx or timeout.

On the API side:

* per-IP and per-account login rate limits;
* one active login attempt per account/request key where practical;
* short database operations;
* no email, RevenueCat, Twilio, or other nonessential work blocking the login response;
* return `503` for temporary database trouble instead of a misleading credentials error.

### 5. Add saturation monitoring

You need visibility before users report the outage.

At minimum, monitor:

* total pool clients;
* idle clients;
* checked-out clients;
* requests waiting for a client;
* connection-acquisition time;
* query duration;
* API response duration;
* timeout count;
* login failures by category;
* database connection errors;
* Railway restarts.

If Neon is in use, its monitoring now includes pooled client and server connection graphs, which can help distinguish application demand from actual Postgres connection use. ([Neon][3])

### 6. Add graceful degradation

When the database is saturated:

* health checks should distinguish basic process health from database readiness;
* `/api/healthz` may remain a lightweight liveness test;
* add a protected or internal readiness check that performs a very short DB query;
* the app should show:

  > “We’re having trouble connecting right now. Your account is safe. Please try again shortly.”
* do not leave users spinning for a minute;
* do not tell them their password is wrong unless authentication actually failed.
