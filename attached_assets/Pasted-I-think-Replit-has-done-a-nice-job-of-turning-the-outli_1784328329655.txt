# 2. Where Should the Slide Archive Live?

**Decision: Separate Registry Folder**

Do **not** embed the archive inside the Foundations Book.

Instead create a dedicated documentation structure.

Example:

```text
/docs
    /Foundations
    /Registry
        DeckRegistry
        SlideRegistry
        CopyLibrary
        AssetRegistry
        Archives
```

The Foundations Book should reference these registries.

It should not become the registry itself.

The Foundations Book explains the system.

The Registry stores the system.

---

# 3. Where Should Metadata Live?

**Decision: Central Registry**

Metadata should not depend on hidden PowerPoint notes, Figma comments, or slide metadata.

Those are fragile.

Instead:

Every approved slide should have a corresponding registry entry.

Think of it like source code.

The deck is the interface.

The registry is the database.

The registry becomes the single source of truth.

---

# 4. Should Existing Slides Receive IDs?

**Decision: Yes.**

Assign IDs to every approved slide that exists today.

Do not wait for new work.

Otherwise we create two systems:

Old slides.

New slides.

That becomes confusing very quickly.

The registry should begin with a complete inventory.

Future slides simply continue the numbering convention.

---

# 5. Should the Copy Library Be Markdown or Database?

**Decision: Both — but in stages.**

### Phase One

Markdown.

Human readable.

Version controlled.

Easy to review.

Easy to approve.

Easy to diff.

### Phase Two

Generate a structured data representation from the approved markdown.

That structured version can later support:

* website
* app
* AI
* search
* documentation
* localization
* automation

The markdown remains the canonical editable version.

The structured data becomes the machine-readable version.

Never make the database the only editable source.

# 64. Decision Log

One of the biggest challenges in long projects is remembering:

> "Why did we decide this?"

Create a Decision Log.

Every major architectural, branding, product, legal, and storytelling decision should receive an entry.

Each record should include:

* Decision ID
* Date
* Decision
* Reasoning
* Alternatives considered
* Tradeoffs
* Approved by
* Related documents
* Related decks
* Related features
* Status
* Whether the decision is still current

Example:

```text
DEC-0021

Decision:

Rename beta testers to Founding Community Members.

Reason:

Better reflects the mission and emotional experience.

Alternatives:

Beta Tester
Early Access User
Founding Explorer

Approved:

Founder

Status:

Active

Related Documents:

Foundations Book

Related Decks:

Community
Business
Zoom
Experience
```

Over time, this becomes an invaluable historical record. It will also help onboard future team members and explain *why* choices were made.
