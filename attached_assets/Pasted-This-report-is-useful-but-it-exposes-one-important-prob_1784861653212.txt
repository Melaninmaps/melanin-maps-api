**The navigation instrumentation cannot be observed in VC68 because those `[NAV-DIAG]` logs were added after VC68 was built.** Waiting for them on the currently installed build will never clear Gate 2.

To avoid another expensive build whose only purpose is collecting logs, I recommend this path:

## 1. Capture the HBCU crash from VC68 now

You do not need a new build for this.

Use either:

* Google Play Console → **Monitor and improve → Android vitals → Crashes and ANRs**, or
* connect the Android phone to the Mac and capture `adb logcat` while reproducing the HBCU crash once.

Do not repeatedly trigger the crash.

## 2. Do not create a diagnostic-only Play build

A diagnostic build would consume more time and another version code merely to prove a navigation sequence that the source already strongly supports.

For the login flicker, choose the deterministic correction—not another timing workaround.

### Use Option A2, not A1

I recommend:

```ts
await refreshUser();
router.replace("/(tabs)");
```

I do **not** recommend:

```ts
setTimeout(() => router.replace("/(tabs)"), 0);
```

A zero-delay timer is another timing-based workaround. It may work on one Android device and fail on another under different scheduling conditions.

Awaiting the profile load means:

* the token is already stored;
* the user state is populated;
* `isAuthenticated` is true;
* the AuthGate cannot redirect back to Login;
* only one final navigation occurs.

The added delay of a few hundred milliseconds is preferable to a visible login-screen flash and repeated map mount/unmount cycles.
