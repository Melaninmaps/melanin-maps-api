The report is strong, but it uncovered an important issue: **do not place a Google Geocoding web-service key directly in `EXPO_PUBLIC_GOOGLE_MAPS_KEY` for this REST request.**

The proposed “iOS bundle ID restriction + Geocoding API” approach may not secure this request correctly. The code is calling Google’s **Geocoding web service** directly over HTTPS from JavaScript. Google’s guidance distinguishes web-service APIs from native Maps SDK calls, and web-service requests are generally protected with server-side restrictions such as IP addresses—not iOS bundle restrictions. A key embedded in the app bundle can also be extracted. ([Google for Developers][1])

## Best decision for Build 94

Proceed as follows:

### Add now

Add `EXPO_PUBLIC_API_URL` to the EAS production environment. That value is a public production origin and is appropriate for an `EXPO_PUBLIC_*` variable.

Keep:

```json
"channel": "production",
"environment": "production"
```

Expo confirms that explicitly using the production environment makes its variables available to the build. Later OTA commands should also specify:

```bash
eas update --environment production
```

so the update bundle uses the same production variables. ([Expo Documentation][2])

### Do not add yet

Do not add `EXPO_PUBLIC_GOOGLE_MAPS_KEY` using:

* the Railway/Replit server key,
* the Android native Maps key,
* the website-referrer key, or
* a new unrestricted Geocoding key.

Instead, route reverse-geocoding through your protected production API. The mobile app should send latitude and longitude to your server, and your server should call Google Geocoding with the existing server-side key. This keeps the key out of the downloadable app bundle and allows proper server-side controls.

## Does this block Build 94?

It depends on whether GeoSafe must work in this beta:

* If GeoSafe already behaved this way in Build 93 and is not a launch-critical testing requirement, you can proceed with Build 94 after adding `EXPO_PUBLIC_API_URL`. Record GeoSafe as a known degraded feature.
* If testers must validate GeoSafe in Build 94, pause and implement the small server proxy first.

I would lean toward **proceeding with Build 94 after adding only `EXPO_PUBLIC_API_URL`**, because the Maps gap is pre-existing and changing the network architecture immediately before this build introduces more risk than the OTA-channel change itself.
