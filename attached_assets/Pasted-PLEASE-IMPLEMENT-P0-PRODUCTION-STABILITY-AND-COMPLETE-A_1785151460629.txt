PLEASE IMPLEMENT — P0 PRODUCTION STABILITY AND COMPLETE APPLE
REJECTION-PREVENTION REVIEW

This supersedes any instruction to merely restart Railway and resubmit.

A manual restart is emergency recovery only. It is not an acceptable
production solution.

Do not create an EAS build and do not resubmit to Apple until every
release gate below is supported by actual evidence.

══════════════════════════════════════════════════════════════
PART 1 — RESTORE SERVICE, THEN IDENTIFY THE ROOT CAUSE
══════════════════════════════════════════════════════════════

You may restart the Railway API service once to restore production access
for diagnosis and testing.

Immediately afterward, perform a root-cause investigation of the recurring
database failures and connection-pool exhaustion.

Determine, with evidence:

1. Railway PostgreSQL plan and maximum permitted connections
2. Current active, idle, and waiting database connections
3. Number of running API replicas/processes
4. Whether each API process creates its own pool
5. Maximum possible combined pool size across all processes
6. Whether any code creates pools repeatedly instead of once at startup
7. Whether database clients are checked out and not released
8. Whether transactions remain open
9. Long-running or blocked queries
10. Idle-in-transaction sessions
11. Connection age and recycling behavior
12. Railway API or Postgres restarts and maintenance events
13. Memory or CPU pressure
14. Deployment events correlated with outages
15. Whether the database itself restarted
16. Whether DNS/internal-network interruptions occurred
17. Whether the application continues using stale connections
18. Whether healthz incorrectly returns OK when database access is broken

Inspect PostgreSQL activity and Railway metrics using safe read-only
queries. Do not expose credentials or user data.

A retry helper is resilience protection. It is not the root-cause fix.

Return a confirmed cause or clearly state which causes remain unproven.

══════════════════════════════════════════════════════════════
PART 2 — IMPLEMENT THE SUSTAINABLE DATABASE CORRECTION
══════════════════════════════════════════════════════════════

Based on evidence, implement the smallest sustainable correction.

Potential corrections may include, only when supported:

- Fixing a connection leak
- Ensuring one shared pool per API process
- Correctly releasing checked-out clients
- Closing abandoned transactions
- Reducing per-process pool size
- Coordinating total connections across replicas
- Adding pool error handling
- Replacing stale connections
- Adding database-aware health and readiness checks
- Preventing traffic before DB readiness
- Adding bounded retry with jitter for transient connection failures
- Correcting Railway service configuration
- Increasing database capacity only if usage proves it necessary

Do not guess.
Do not simply increase pool limits.
Do not hide persistent failure behind repeated retries.
Do not broadly refactor unrelated database code.

The health endpoint must distinguish:

- API process alive
- Database reachable
- Application ready to serve authenticated requests

A database outage must not return a misleading overall “ok.”
