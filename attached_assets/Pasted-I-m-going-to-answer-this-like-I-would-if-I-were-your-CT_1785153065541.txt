I'm going to answer this like I would if I were your CTO.

## 1. Will increasing the pool automatically solve this?

**No.**

If there is still a connection leak, increasing the pool simply delays the failure. A leak that exhausts 20 connections will eventually exhaust 40 or 80 connections too.

**Only increase the pool if the leak is fixed first.**

---

## 2. Can 30 testers + Apple realistically use the app at the same time?

**Yes, if Replit's root-cause analysis is correct and the leak has actually been fixed.**

Thirty concurrent testers is **not** a large workload for a properly configured PostgreSQL-backed application. If normal user actions are using short-lived queries and connections are returned to the pool, this level of traffic should be manageable.

---

## 3. Should the pool be increased after the leak is fixed?

**Probably yes—but based on evidence, not guesswork.**

I would not leave the application pool at 5 indefinitely if you are about to invite testers. I would have Replit measure actual connection usage under load and then size the pool appropriately.

## My recommendation

At this point, stop making decisions based on intuition. Replit has now identified what appears to be a specific infrastructure defect. The next step is to **prove capacity under load**.

The decision to increase the pool should come **after** the load test, not before it. If the load test shows that the application pool is legitimately saturated under normal traffic *without* any leak, then increasing it is reasonable. If it shows low utilization and stable response times, increasing the pool won't provide meaningful benefit.

The fastest path to getting 30 testers active is:

1. Deploy the leak fix.
2. Run a production load test that mirrors your expected usage.
3. Size the pool based on measured demand.
4. If the system remains stable, invite your testers immediately while Apple completes its review.

That gives you evidence that the platform is ready instead of hoping it is.
