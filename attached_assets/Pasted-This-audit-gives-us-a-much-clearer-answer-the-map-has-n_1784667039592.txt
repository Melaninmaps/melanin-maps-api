This audit gives us a much clearer answer: **the map has not been fixed yet, and the app is not ready for Apple.**

The most important new finding is that the database failures returned about 30 minutes after the Railway restart, even though there were no new deployments. The health check remained fast, while every database-dependent route timed out again. That means restarting Railway only temporarily cleared the symptoms. 

## What we now know about the map

The mobile app uses `react-native-maps` with the default provider. On iOS, that means Apple Maps, so the base map should not require the Google Maps JavaScript key that was previously being discussed. 

That corrects an important earlier assumption:

* `/api/maps/js-key` is not what powers the iPhone’s base map.
* Adding a Railway Google Maps key will not automatically fix the black mobile map.
* The problem is more likely within the mobile map component, one of its attached hooks, or its rendering state.

The audit also found an existing `/map-diagnostic` screen that renders only the raw Apple map, without markers, overlays, or API hooks. That is exactly the right next test:

* If the diagnostic screen renders normally, the native map setup is good and one of the app hooks or overlays is breaking the full map.
* If the diagnostic screen is also black, then it is a native configuration problem that may require another build. 

## Two concerns in Replit’s proposed conclusions

### 1. The pool problem is confirmed, but the exact cause is not

Replit has good evidence that database connections are becoming unavailable. However, it has **not yet proven** that the cause is specifically “no statement timeout.”

Its own report lists several possible causes:

* a long-running query
* an unfinished transaction
* a cron or monitoring job
* simultaneous slow queries
* a route that repeatedly saturates the five-connection pool 

Adding a statement timeout may protect the server from indefinitely slow queries, but it is not enough by itself unless Replit identifies:

* which SQL query is holding connections,
* which route triggered it,
* how long the query ran,
* and whether any cron job is repeatedly recreating the condition.

We should not approve a server PR based only on the current hypothesis.

### 2. There is a configuration inconsistency that must be resolved

The audit says `FullMapView` reads `EXPO_PUBLIC_DOMAIN`, and it concludes that variable may be missing. 

But in the earlier pre-build report, Replit said `EXPO_PUBLIC_DOMAIN` was already present in the production build environment. Those two statements conflict.

Before adding anything, Replit must confirm the **resolved value used when Build 94 was actually bundled**, not merely what exists in the current file or Expo dashboard.
